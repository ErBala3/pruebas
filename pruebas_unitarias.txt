Este documento describe todas las pruebas unitarias preparadas para el sistema
QRAccess, organizado por sub-aplicación. En total hay 90 pruebas repartidas en
tres conjuntos de tests.

Cómo ejecutar cada suite:

  backend/      →  cd backend      && npm test
  qraccess/     →  cd qraccess     && npm install && npm test
  fichaje_qr/   →  cd fichaje_qr   && python -m pytest tests/test_fichaje.py -v

1. BACKEND NODE.JS  (archivo: backend/api.test.js)  —  35 pruebas
--------------------------------------------------------------------------------

Esta suite usa Jest + Supertest para probar la API REST del backend principal.

── AUTENTICACIÓN (POST /api/auth/login) ─────────────────────────────────────

  1. login correcto devuelve token JWT
     Envía usuario "admin" y contraseña "admin123". Comprueba que la respuesta
     tiene código 200 y contiene un campo "token" en el cuerpo JSON.
     Propósito: verificar que el flujo de login feliz funciona correctamente.

  2. credenciales incorrectas devuelve 401
     Envía contraseña incorrecta. Comprueba código 401 y campo "error".
     Propósito: el sistema debe rechazar credenciales inválidas.

  3. campos vacíos devuelve 400
     Envía body vacío {}. Comprueba código 400.
     Propósito: la validación de entrada debe rechazar peticiones sin datos.

── EMPLEADOS (CRUD) ──────────────────────────────────────────────────────────

  4. GET /api/employees sin token devuelve 401
     Petición sin cabecera Authorization. Comprueba código 401.
     Propósito: los endpoints protegidos no deben ser accesibles sin JWT.

  5. GET /api/employees con token devuelve lista
     Petición con JWT válido. Comprueba código 200 y que el cuerpo es un array.
     Propósito: un admin autenticado puede listar empleados.

  6. POST /api/employees crea empleado con qr_token único
     Crea el empleado "María Test". Comprueba código 201, presencia de "id" y
     "qr_token", y que el token cumple el patrón /^emp_[a-zA-Z0-9]+$/.
     Propósito: la creación genera un token QR con el formato correcto.

  7. POST /api/employees sin nombre devuelve 400
     Body vacío en la creación. Comprueba código 400.
     Propósito: el campo "name" es obligatorio.

  8. GET /api/employees/:id devuelve el empleado correcto
     Consulta por ID el empleado recién creado. Comprueba que el nombre coincide.
     Propósito: el endpoint por ID devuelve el recurso exacto pedido.

  9. PUT /api/employees/:id actualiza el nombre
     Actualiza el nombre a "María Actualizada". Comprueba código 200 y que
     el nombre en la respuesta es el nuevo valor.
     Propósito: la edición de empleado funciona y persiste el cambio.

 10. PUT /api/employees/:id con status inválido devuelve 400
     Intenta actualizar status a "suspendido" (valor no permitido). Comprueba
     código 400.
     Propósito: la validación del campo status solo permite "active"/"inactive".

 11. PUT /api/employees/:id inexistente devuelve 404
     Intenta actualizar el empleado con ID 99999. Comprueba código 404.
     Propósito: actualizar un recurso que no existe debe dar error claro.

 12. DELETE /api/employees/:id elimina el empleado
     Crea un empleado extra, lo elimina y verifica que un GET posterior devuelve
     404.
     Propósito: el borrado es efectivo y el recurso deja de existir.

 13. DELETE /api/employees/:id inexistente devuelve 404
     Intenta borrar ID 99999. Comprueba código 404.
     Propósito: borrar algo que no existe debe devolver error, no fallar en
     silencio.

 14. GET /api/employees/:id inexistente devuelve 404
     Consulta ID 99999. Comprueba código 404.
     Propósito: consultar un recurso que no existe debe dar 404.

 15. GET /api/employees/:id/qr devuelve el qr_token del empleado
     Comprueba código 200, presencia de "qr_token" y que "employee_id" coincide
     con el ID solicitado.
     Propósito: el endpoint QR devuelve el token correcto.

 16. GET /api/employees/:id/qr con ID no numérico devuelve 400
     Solicita /api/employees/abc/qr. Comprueba código 400.
     Propósito: los parámetros de ruta deben validarse como enteros.

================================================================================
  TIPOS DE PRUEBA CUBIERTOS
================================================================================

  · Pruebas de camino feliz (Happy path)
    Verifican que la operación principal funciona cuando se dan los datos
    correctos (login correcto, crear recurso, fichar, etc.).

  · Pruebas de validación de entrada
    Comprueban que los campos obligatorios son rechazados cuando faltan o
    tienen formato incorrecto (email vacío, ID no numérico, fecha inválida,
    nombre demasiado largo, token con longitud incorrecta).

  · Pruebas de autenticación y autorización
    Verifican que los endpoints protegidos devuelven 401 cuando no hay token,
    403 cuando el rol es insuficiente, y que tokens manipulados o expirados
    son rechazados.

  · Pruebas de lógica de negocio
    Verifican la lógica de alternancia IN/OUT de los fichajes, la protección
    anti-duplicado (ventana de 5-10 segundos), que empleados inactivos no
    pueden fichar, y que cada usuario tiene su propio estado de fichaje.

  · Pruebas de recursos no encontrados (404)
    Consultar, actualizar, borrar o fichar con IDs/tokens que no existen debe
    devolver siempre 404 y no un error 500 ni un silencio incorrecto.

  · Pruebas de integración de endpoints
    Flujos encadenados (crear empleado → obtener QR → fichar → comprobar
    historial) que verifican la coherencia del sistema end-to-end dentro de
    la suite.
